# taxi-pitstopmap 설계서

> 택시 기사를 위한 주정차 가능 식당·화장실 안내 서비스

## 1. 문제 정의와 핵심 가치

- **문제**: 택시 기사는 식사와 화장실이 급한데, 근처 식당이나 화장실이 있어도 차를 세울 곳이 없어 헤매거나 주정차 단속을 걱정한다.
- **핵심 가치**: "지금 내 위치에서 차를 세우고 바로 이용할 수 있는 곳"을 빠르게 보여준다.
- **차별점**: 기존 지도 앱은 "장소"는 알려주지만 "주정차 가능 여부"는 알려주지 않는다. 이 앱의 핵심은 주정차 정보다.

## 2. 가장 큰 리스크: 주정차 데이터

무료 API에서 "이 식당 앞에 주정차 가능"이라는 정보를 직접 주는 곳은 없다. 그래서 세 가지 데이터를 조합하는 구조가 필요하다.

| 데이터 층 | 출처 | 신뢰도 |
|---|---|---|
| ① 공식 데이터 | 공공주차장, 주정차 허용/금지 구간 (공공데이터포털, 서울 열린데이터광장 등) | 높음, 커버리지 낮음 |
| ② 추정 데이터 | 식당 자체 주차장 여부, 인근 공영주차장 거리, 도로 유형(OSM) | 중간 |
| ③ 사용자 제보 | 기사들이 직접 "여기 세울 수 있음/단속됨" 등록 및 확인 | 시간이 갈수록 높아짐 |

**핵심 전략**: 초기에는 ①②로 시작하고, ③(크라우드소싱)으로 데이터를 키운다.

## 3. 기능 정의

### MVP (1차 목표)
1. 현재 위치 기반 지도 표시
2. 주변 식당·화장실 검색 (반경 500m~2km 조절)
3. 장소별 "주정차 점수" 표시 (🟢 가능 / 🟡 불확실 / 🔴 어려움)
4. 장소 상세: 주소, 영업시간, 주차 정보, 지도 앱(카카오맵·네이버 지도·T맵) 연결
5. 필터: 식당 / 화장실 / 주차 가능만 보기

### 2차
6. 사용자 제보 (주정차 가능/불가, 단속 여부, 화장실 청결도)
7. 즐겨찾기, 최근 이용 장소
8. 24시간 영업 식당 필터 (야간 근무 기사에게 중요)
9. 음성 안내 및 큰 버튼 UI (운전 중 조작 최소화)

### 3차 (확장)
10. 사용자 평점과 후기, 신뢰도 시스템
11. 시간대별 단속 정보
12. 콜 대기 시간에 맞춘 추천

## 4. 시스템 아키텍처

```
[모바일 웹앱 (PWA)]
        │
        ▼
[백엔드 API 서버]  ──►  [DB (PostgreSQL + PostGIS)]
        │
        ├─► 카카오 로컬 API (식당·장소 검색)
        ├─► 공공데이터포털 (공중화장실, 주차장 표준데이터)
        ├─► OpenStreetMap / Overpass API (도로·화장실 보완)
        └─► 지도 SDK (카카오맵 JS SDK)
```

**추천**: 처음엔 네이티브 앱보다 PWA(모바일 웹)로 시작한다. 스토어 심사 없이 바로 배포·테스트할 수 있고, 나중에 앱으로 감싸는 것도 가능하다.

## 5. 기술 스택

| 영역 | 추천 | 이유 |
|---|---|---|
| 프론트엔드 | Next.js + TypeScript + Tailwind | AI 코딩 도구와 궁합이 좋고 자료가 많음 |
| 지도 | 카카오맵 JS SDK | 국내 데이터 정확도 |
| 백엔드/DB | Supabase (PostgreSQL + PostGIS + 인증) | 무료 티어, 위치 기반 쿼리 지원 |
| 배포 | Vercel | 무료, GitHub 연동 자동 배포 |
| 데이터 수집 | Python 스크립트 | 공공데이터 전처리용 |
| 바이브 코딩 도구 | 미정 (Claude, Cursor, Claude Code 등) | 하나만 골라 익숙해지는 것을 권장 |

> 각 API의 무료 사용량과 약관은 자주 바뀌므로 개발 전에 공식 문서에서 확인할 것.

## 6. DB 설계 (핵심 테이블)

```
places (장소)
 ├ id, name, type(restaurant/toilet), lat, lng(geography)
 ├ address, phone, open_hours, is_24h
 ├ source (kakao/public/osm/user)
 └ has_own_parking (bool)

parking_spots (주정차 가능 지점)
 ├ id, lat, lng, type(공영주차장/허용구간/제보)
 └ source, verified_count

place_parking_score (장소별 주정차 점수)
 ├ place_id, score(0~100), nearest_spot_distance
 └ updated_at

reports (사용자 제보)
 ├ id, place_id, user_id, report_type
 ├ content, created_at
 └ upvotes, downvotes

users
 └ id, nickname, trust_level
```

**주정차 점수 계산 예시**: 자체 주차장 있음(+40) + 100m 내 공영주차장(+30) + 최근 30일 내 "가능" 제보(+30) − "단속됨" 제보(−40)

## 7. 화면 설계 (MVP)

1. **메인(지도)**: 내 위치 중심 지도, 마커는 주정차 점수 색상으로 표시, 하단에 식당/화장실 토글과 가까운 순 리스트
2. **장소 상세**: 이름, 거리, 주정차 점수와 근거("자체 주차장 있음", "80m 앞 공영주차장"), 지도 앱 연결 버튼(카카오맵·네이버 지도·T맵, 길안내는 각 앱에서), 제보 버튼
3. **제보 화면** (2차): 원터치 선택형 ("세울 수 있었음 / 단속됨 / 자리 없음")

**UI 원칙**: 큰 버튼, 고대비 색상, 최소 탭 수. 운전 중 사용 가능성이 있으므로 텍스트 입력은 최소화한다.

## 8. 개발 로드맵

| 단계 | 기간(예상) | 목표 |
|---|---|---|
| 0. 준비 | 1주 | GitHub 저장소, 프로젝트 세팅, API 키 발급, 데이터 조사 |
| 1. 지도 + 검색 | 1~2주 | 카카오맵 표시, 주변 식당 검색 |
| 2. 화장실 데이터 | 1주 | 공중화장실 데이터 적재 및 지도 표시 |
| 3. 주정차 점수 | 2주 | 공영주차장 데이터 연동, 점수 로직 |
| 4. 제보 기능 | 2주 | 로그인, 제보, 점수 반영 |
| 5. 다듬기·배포 | 1~2주 | PWA 설정, UI 개선, Vercel 배포 |
| 6. 실사용 테스트 | 진행 | 실제 택시 기사 3~5명 피드백 |

처음에는 **한 개 지역(예: 서울 강남구)만** 대상으로 한다. 데이터 품질 관리와 테스트가 훨씬 쉽다.

## 9. GitHub 관리 전략

- 브랜치: `main`(배포) / `dev`(개발) / `feature/*`
- 커밋 메시지 규칙: `feat:`, `fix:`, `docs:`, `chore:`
- GitHub Issues + Projects로 작업 관리
- README 포함 항목: 문제 정의, 스크린샷/GIF, 아키텍처 다이어그램, 기술 선택 이유, 트러블슈팅 기록
- `docs/` 폴더에 설계서와 의사결정 기록 보관
- API 키는 `.env`로 관리하고 커밋하지 않기 (`.gitignore` 필수)
- 라이선스: 판매 가능성을 고려해 당분간 **None (All Rights Reserved)** 유지

## 10. 카카오 제안에 대한 현실적 조언

- 카카오T가 이미 택시 기사 앱을 운영하므로 아이디어만으로는 어렵다. **동작하는 데모 + 실제 사용자 데이터/피드백**이 필요하다.
- 무료 API 사용 시 **이용약관과 상업적 사용 조건**을 사전에 확인한다.
- 현실적인 경로: ① 포트폴리오 → ② 카카오모빌리티 공모전·스타트업 프로그램·제휴 제안 → ③ 소규모 실사용자 확보 후 협상
- 사용자 제보 DB가 이 프로젝트의 핵심 자산이므로 초기부터 데이터 품질 관리에 신경 쓴다.
